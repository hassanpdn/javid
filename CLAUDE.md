# Javid school AI demo

Demo of AI assistants, listed as cards after the live site's door: an elementary school (the main one, described below), a fabric wholesaler (`fabric/`, see its section), a deed data extraction assistant (`deed/`, see its section), a real estate agency (`estate/`, see its section), a law office (`law/`, see its section), a dental clinic (`dental/`, see its section), a hotel (`hotel/`, see its section) and an eco-lodge with its own public website (`lodge/`, see its section). For the school, the default is Javid non-profit elementary school (مدرسه غیرانتفاعی جاوید), Tehran; the first screen is a setup form where the demo is set up for any school (name, boys or girls, city, district, manager, counselor and staff names). Every role has its own login and panel. All data is fake and generated by `seed.py`.

## Run

```
python3.12 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env          # then edit
python seed.py                # wipes and rebuilds school.db with demo data
python ingest.py              # chunks docs/ into the Chroma vector db (./db)
uvicorn app:app --reload      # http://localhost:8000
```
Frontend (Node 20.19+, pnpm), only needed when changing the UI:
```
cd frontend && pnpm install
pnpm dev                      # http://localhost:5173, hot reload, API calls proxied to :8000
pnpm build                    # writes the finished site into ../static (committed, so the demo needs no Node)
```
Tests (no Ollama needed: a fake model in `tests/fake_llm.py` stands in, and can misbehave on purpose):
```
pip install -r requirements-dev.txt
pytest                                        # API, privacy, checks, validation, dates, concurrency
cd frontend && pnpm exec playwright install chromium   # once
PYTHON=../.venv/bin/python pnpm test:e2e      # browser tests for every role
```
The demo follows the real date: `seed.py` builds everything around today, and the server rebuilds the data on startup when it was made on another day. `DEMO_TODAY` pins a date, `KEEP_DB=1` keeps old data. The school's details live in `school.json` (per machine, not committed; `SCHOOL_PATH` moves it). It holds only the school being shown: the demo is given to different schools, so no school may ever see another school's name (no saved list, nothing named on the setup form, Javid's details only behind «تنظیمات پیش‌فرض»). Without the file the app opens on the setup form and `GET /school` gives nothing out. Only Hassan runs the demos, so the setup form has no password. Runtime role switches (`POST /features`, «چه کسانی وارد شوند» on the login page and in the setup's last step) turn the parent and student roles off at once, without rebuilding data: with both off the app is an internal CRM for the school staff. Server side, `school.role_enabled` blocks login and ends sessions of switched-off roles (`auth.current_user`), parents drop out of referral recipients, and counselor messages to parents return 403. On the live server two more switches are on, both off by default (local runs and tests): `SITE_USER`/`SITE_PASSWORD` turn on the site's door (`gate.py`, `GatePage.vue`): every API call except `/gate/*` returns 401 `{"detail":"site"}` until the browser has the door's signed cookie (30 days); the password lives only in the server's `.env`, never in the repo. `ADMIN_USER`/`ADMIN_PASSWORD` turn on a login for each assistant (`access.py`, `lib/access.js`): the permanent account (checked first at the door too, so one login opens everything) sees every card and «دسترسی‌ها» below them (`AccessManager.vue`, `AccessForm.vue`), where it gives people accounts: name, username, password, one or more assistants, an optional expiry date and time (Jalali «1405/08/30 18:30», picked with `core/DatePicker` and `core/TimePicker`, empty = no expiry; «today» comes from the server's clock in Tehran, `GET /access/status`, never the visitor's computer). Anyone else sees only their own cards (full access inside); someone through the door without an account gets a login box (`AccessDialog.vue`). Changes apply on the next call; a new password, deletion or the expiry passing end their logins. The API answers 401 `{"detail":"access","app":...}` otherwise. Every login try at the door or a card's login box goes into the same database's `logins` table (`access.record_login`: who, when, result ok / wrong password / expired / unknown username, door or card, a short device label from the user agent, the IP kept but never sent; 90 days kept), shown only to the permanent account in «ورودها» below «دسترسی‌ها» (`LoginLog.vue`, `GET /access/logins`, 50 at a time, filter by person); its own logins appear as «حساب دائمی», the door's shared password as «رمز سایت». Real visitors' speed: behind the door, each screen (the assistants page and every assistant's panel, not the door, login or setup pages) reports from the visitor's own browser how many ms until it was usable, KB, failed requests, phone or computer and connection type (`lib/rum.js`, `ready()` from `retryable`, HubPage and DeedApp; nothing from automated browsers) to `POST /speed` (`speed.py`, 30 a minute per address, 90 days in `access.db`); the permanent account sees per screen the median, the slowest tenth and failures in «سرعت برای بازدیدکنندگان» (`SpeedPanel.vue`, `GET /speed`). Accounts live in `access.db` (`ACCESS_DB_PATH`), which resets and reseeding keep. The same database holds each assistant's AI switch, under its card for the permanent account only (`access.ai_on`, `POST /access/ai`): off by default on the live site, always on without `ADMIN_PASSWORD`. Off, `llm.ask_llm` raises `ModelOff` (the request's assistant comes from `llm.assistant`, set in `app.py`) and nothing goes to the model or the embedding API; by Hassan's choice the screens stay exactly the same and show texts built by code from real data only (`offline.py`: document answers quote the best-matching article or say «not found», letters are read by keywords, warnings and counselor drafts come from templates), with no sign of the switch to anyone else. `RESET_ON_LOAD=1` makes every page load call `POST /setup/reset` (forgets the school, logs everyone out), so each visit starts on an empty setup form; without it the endpoint is 404. Other settings: `SHOW_DOCS=1` turns on /docs, `ALLOWED_ORIGINS` allows other sites to call the API, `SESSION_DAYS` (default 7).
Models run in Ollama on the Mac: `qwen3-14b` (chat) and `bge-m3` (embeddings), both through the OpenAI-compatible API. The model gets `LLM_TIMEOUT` seconds (default 15, under the browser's 20 s for a read) and no silent retries; a timeout or a provider error raises `llm.ModelDown`, a kind of `ModelOff`, so every screen answers with the same code-built text as with the AI switched off (`/chat` too, and its embedding call), keeps none of it, and tries the model again on the next request. Python 3.15 breaks chromadb builds; use 3.12. Demo users all have password `1234` (modir, edari, moalem, karimi, moshaver, vali, daneshamooz, plus teacher{id} and parent{student_id}).

## The fabric wholesaler (`fabric/`, `frontend/src/fabric/`)

A Tehran fabric wholesaler (عمده‌فروشی پارچه) with customers all over Iran, who works with three Excel files and the phone. Everything is simulated and Hassan has said not to ask before choosing details: real customers will change it anyway.
- Its own everything: settings in `fabric.json` (`FABRIC_PATH`), database `fabric.db` (`FABRIC_DB_PATH`), the three workbooks in `fabric_files/` (`FABRIC_DIR`), logins `sahebkar` (owner), `forooshande` (seller), `hesabdar` (accountant), password `1234`. A school token never works on `/fabric/...` and the other way round; the frontend keeps `fabricSession` beside `session` (`lib/api.js` picks the token by path).
- `excel.py` builds four months of business into انبار/فروش/حسابداری.xlsx (with planted situations: a bounced cheque from the biggest buyer, a customer over his credit limit, a fabric about three days from running out, dead stock, next week's cheques not covered, a regular customer gone quiet), then reads them back like a stranger's files: names written several ways, Persian digits, a hand-typed total row; each fix becomes an import note shown in the panels. A sale confirmed at the phone desk is written into all three files.
- `facts.py` computes every number; money is always worded by `money()` (e.g. «۱۲۸ میلیون تومان») so model text can be checked with `checks.only_known_numbers`. Model text that fails, or no model answer, falls back to text built in code (`_written` in `api.py`).
- The wholesaler had a theft, so the demo is built around trust: `facts.reconcile()` checks the three files against each other (stock: opening + deliveries − sold = on the shelf; invoice numbers without gaps; each day's cash sales = that day's deposit in «صندوق»; every cheque sale has its cheque). `PLANTED` leaves the marks a theft leaves (an invoice removed from the sales file whose fabric still left the warehouse, one evening's cash short) and the checks find them from numbers alone. Findings say what does not add up and show the sum, never who did it. Every number on the owner's dashboard and in reports has «از کجا؟» (`HowTip`) with the sum and the sheet each part comes from. Every change goes into `events` with who and when (`store.log`); the owner sees it live («هم‌اکنون») and in «تطبیق». The seller does not see checks or the log.
- «سایت فروشگاه» (`shop.py`, `ShopView.vue`): the shop's website as an end customer sees it, with an assistant that takes orders in short sentences, asks only what it needs (which colour, how many rolls, a mobile number; a known number is recognised) and gives an order number. The model only reads what the customer wrote; prices, stock and totals are written by code from the stock file, and «پشت صحنه» shows which file each answer came from. An order goes into `web_orders` and the sales file's «سفارش‌های سایت» sheet as «پرداخت نشده», is logged, and owner and seller get a toast and a badge (`webOrders.js`). Once paid, «پرداخت شد، ثبت فاکتور» makes a normal invoice through `api.make_invoice` (a new customer is added to the accounts file first). Website orders are not invoices, so they do not touch stock or the reconciliation until then.
- The live site resets it with the school (`RESET_ON_LOAD`). Locally the assistants page only shows with `HUB=1`; without it the school opens straight away, so the school's e2e tests are unchanged. `tests/test_fabric.py` covers it.

## The deed data extraction assistant (`deed/`, `frontend/src/deed/`)

A demo for the Registration Organization (سازمان ثبت اسناد و املاک): a reviewer sends a scanned booklet deed (image, PDF or pasted text), reviews the extracted data next to the scan, confirms, and downloads JSON for the single-page deed. Details, running and known limitations in `deed/README.md`.
- No login of its own (the card's login in `access.py` covers it), one kind of user. Its own `deed.db` (`DEED_DB_PATH`) and files (`DEED_DIR`); the live site forgets every deed on each visit (`deed_api.reset` in `/setup/reset`) and on every logout (`/gate/logout`, `/access/logout`), for everyone: it is a demo.
- OCR on the server only: Tesseract (`fas`, `osd`) and poppler as command-line tools (`deed/ocr.py`), one page at a time, cached by page hash.
- Extraction by rules (`deed/extract.py`), or by the model through `llm.py` when the card's AI switch is on (validated against `fields.PageData`, one retry, then an error; no answer falls back to rules). Every value is then looked for in the page's text: not there means null, never a guess; there gives its source line and a confidence from the OCR. Dates Jalali and real, national ID check digit, shares add up to 6 dang, pages that disagree keep both values.
- The three samples in `deed/samples/` are drawn by `python -m deed.make_samples` (Pillow with libraqm) and committed. `tests/test_deed.py` covers it (OCR tests skip without Tesseract).

## The real estate agency (`estate/`, `frontend/src/estate/`)

A neighbourhood agency (بنگاه املاک) in west Tehran (پونک، شهرک غرب، سعادت‌آباد، جنت‌آباد، شهران, fixed in `agency.HOODS`) with an owner and two agents, built around what goes wrong in a traditional agency: listings lost or entered twice, sold units still offered, buyers matched from memory, owners left without news, prices guessed, and deals taken around the agency. Sale and rent both.
- Its own everything, like the fabric shop: settings in `estate.json` (`ESTATE_PATH`), database `estate.db` (`ESTATE_DB_PATH`), logins `modir` (owner), `moshaver1`, `moshaver2` (agents), password `1234`, `estateSession` in `lib/api.js` for `/estate/...`. Card «دستیار بنگاه املاک» on the assistants page; `access.APPS` has `estate`; the live site resets it with the rest.
- `demo.py` builds the agency's work around today (fixed seed): about 125 listings, 65 buyers and renters, 160 past deals (the price history), visits and calls. Planted, each found exactly once: a duplicate listing, a listing with no call to its owner for 52 days, an overpriced one, a new listing nobody offered to the buyer it fits, tomorrow's unconfirmed visit, an owner without a report for 41 days, a «deal around the agency» pattern (withdrawn days after a customer's third visit, that customer's request closed as lost), and a commission written well under the tariff.
- `facts.py` computes everything: `match()` (neighbourhood required, budget with a little room, missing rooms, area or features said in words), `price_check()` (price per m², or the whole monthly rent per m² with the deposit converted, against the agency's own deals in that neighbourhood, similar age when there are three; «از کجا؟» lists the deals), deposit and rent `convert()`, `commission()` and its split, `alerts()` (today's work, per agent too) and `checks()` (owner only; says what does not add up, never who did it). Rate and tariff are settings (default 3% a month, 0.5% of a sale and 25% of a month's rent from each side), to be checked against the union's tariff.
- `read.py`: a listing or a request from pasted text (Divar ad, WhatsApp message, call notes). The model reads it when the card's AI is on, rules otherwise; every value must be in the text (numbers, amounts, a neighbourhood or name written there), else it stays empty; each comes back with the words around it, shown under the field. A pasted listing shows look-alike units before saving.
- Messages are drafts the agent sends (visit confirmations built by code; the owner's report written by the model from computed facts and checked by `only_known_numbers`, with a code-built fallback); the visit outcome line becomes a note and a next step.
- «سایت بنگاه» (`site.py`, `SiteView.vue`): the agency's website with its assistant. It asks only what it needs, shows the fitting units (code-written; never the owner's name, phone or exact address; listings not confirmed with their owner in 30 days are left out) and takes a mobile number, which becomes a request for an agent in turn, with a toast and a badge (`useLeads`). `tests/test_estate.py` covers it.

## The law office (`law/`, `frontend/src/law/`)

A Tehran law office (دفتر وکالت) built around one fear: a missed deadline. Notices come from the courts' system (ثنا) and each starts a deadline that lives in a notebook or someone's head.
- Its own everything, like the others: settings in `law.json` (`LAW_PATH`), database `law.db` (`LAW_DB_PATH`), logins `vakil` (the lawyer, owner), `hamkar` (associate), `monshi` (secretary), password `1234`, `lawSession` in `lib/api.js` for `/law/...`. One panel for all roles (`LawPanel.vue`); the owner also gets the checks, the settings, the morning summary and the live log; the associate's home shows only their own cases; only lawyers mark work done or write a client's report.
- `facts.deadline()`: the day of service does not count, the last day is service + the days for that kind of notice, and a last day on a Friday or an official holiday moves to the next working day. Days per kind are settings (defaults: 20 for an appeal, a default-judgment objection and a further appeal, 10 for a correction notice and an enforcement order, 7 for objecting to an expert's opinion), and the fixed solar holidays are built in; lunar holidays move every year and are entered in «مهلت‌ها و تعطیلات». A real office checks these numbers before relying on them. «از کجا؟» on every deadline shows how it was counted.
- `read.py`: a notice from pasted text: kind (by its own words), case number, archive number, branch, court, date of service, hearing date and time. Rules read it, the model may fill what they missed when the card's AI is on, and every value must be written in the text. The case is found by its number. `GET /law/sample` gives a notice for one of the demo's cases, for showing it.
- `demo.py`: about 60 cases with past notices handled in time, and eight planted situations, each found exactly once: an appeal due the day after tomorrow, a correction deadline that passed yesterday, a hearing tomorrow, an expert's opinion entered five days after service, an appeal whose twentieth day is a Friday, a case idle for 75 days, an appeal filed after its last day last month, and a client without news for 40 days.
- The client's report is written by the model from the case's notices and checked by `only_known_numbers`, with a code-built fallback; the lawyer reads and sends it. `tests/test_law.py` covers it.

## The hotel (`hotel/`, `frontend/src/hotel/`)

A luxury hotel on the Caspian coast (Nowshahr): 80 rooms in three types (garden-view and sea-view doubles, triples), 6 suites and 4 villas. Reservations to check-out in one panel, built for busy days; the operator decides, the assistant reads, works out and suggests.
- Its own everything, like the others: settings in `hotel.json` (`HOTEL_PATH`), database `hotel.db` (`HOTEL_DB_PATH`), logins `modir` (manager), `rezerv` (reservations), `paziresh` (front desk), `khanedari` (housekeeping, its own phone page `HousekeepingPanel.vue`: rooms in the order to clean them, repairs, guests' requests), password `1234`, `hotelSession` in `lib/api.js` for `/hotel/...`.
- `facts.py`: a night's price = the type's base price × season (Nowruz 1.6, summer 1.3, quiet months 0.8) × weekend (Wednesday and Thursday nights 1.2) + extra bed + meals per person (half or full board); children under 6 free and without a bed; each booking keeps its nights' prices and closing the day (`POST /hotel/close`) posts tonight's to the folio and sets the cash counted beside the day's cash payments. ## How we work

The code is written fast by a model and nobody else reviews it, so these keep it from drifting.

1. Where code lives.
   - Backend: numbers and rules live in plain functions in their own modules (`students.py`, `stats.py`, `checks.py`, `jalali.py`, `fabric/facts.py`, ...).
   - Routers are thin: check the input and the role, call those functions, return the result.
   - Model calls go through `llm.py`. Model text is checked by `checks.py` before anyone sees it.
   - Frontend: pages and components show data and send actions. They never work out a business number themselves; the server sends it. They reach the server only through `lib/api.js` (or the small `lib/*.js` stores built on it).
   - Shared pieces go in `components/core/` (general) or `components/` (this app).
2. One request, one mode.
   - PLAN: Hassan asks a question, «نظرت چیه», or describes a new feature. Discuss the approach and the spec. Write no code.
   - IMPLEMENT: he says to build or fix something. Do that one narrow task, nothing beside it.
   - REVIEW: he asks for a review. Critique the diff against this file. Change nothing unless he asks.
   - If it is unclear which mode a request is, it is PLAN.
3. Don'ts.
   - No new dependency (pnpm or pip) without asking first. The server installs Python packages from an Iranian mirror, so a new one may not even be installable there.
   - No refactoring, renaming or "cleaning up" of code the request did not mention. If something nearby looks wrong, say so; don't fix it on the side.
   - No code "for the future": no options, settings, hooks or abstractions nothing uses yet.
4. Done means:
   - `pnpm build` passes and the new `static/` is in the same commit.
   - The tests for the part that changed pass (see the testing rule below; the full suite only when Hassan asks or a change touches every panel).
   - A new backend module gets a test file next to the others in `tests/`.
   - A new screen or list was looked at on desktop and at 360px.
   - Then a small commit: one change, one slice through the layers it needs, with a message that says what and why.

## Rules that must not break

- Words on screen are standard written Persian (فارسی معیار, as the dictionaries have it) that any parent, teacher or manager understands at once. Not colloquial: «جدید» not «تازه», «اکنون» or «در حال حاضر» not «الان», «می‌توانید» not «می‌تونید», «را» not «رو», «در» not «توی», «است» not «ـه». Not office jargon either (no «ارجاع», «رؤیت», «صدور», «در دست اقدام», «اعلام وصول»): say «فرستادن», «دیدن», «در حال انجام», «تأیید دریافت». This covers buttons, example questions, built-in answers and what the prompts ask the model to write. What users type stays as they type it (the patterns that read questions still accept colloquial words). Official letter texts the model writes keep their formal tone.
- On phones, check every new list at 360px: no text squeezed beside a tag or running into another line.
- Dropdowns get their arrow from `main.css` (12px in from the edge); don't put back the browser's own.
- Keep the site light: endless animations are CSS keyframes on translate/scale/rotate/opacity, never GSAP; a dialog, drawer or page shown only after a click is `defineAsyncComponent`. When the site feels slow, or a change adds animation, a page or a library, use the `perf-check` skill (`.claude/skills/perf-check`: scripts that measure, and `reference.md` with what was learned).

- Role and identity come from the logged-in user (`require_role`, `user["ref_id"]`), never from the request body or the question.
- Numbers are computed by code; the model only writes text. Model output that contains numbers is checked against the computed facts (stats replies, warning dates, parent answers).
- Human in the loop for anything that leaves the office or is a decision.
- Parents see only their own child. Counselor notes, health-form flags and unapproved suggestions never reach parents or the model in parent flows. No comparison with other students.
- Vector search always filters by `access_{role}`.
- SQLite allows one writer: send notifications after the write transaction commits.
- Never write a school, manager or counselor name into code, prompts or seed data: take it from `school.py` (backend) or `schoolInfo` (frontend).
- Any new model-written text shown to a parent goes through `checks.unsafe_for_parent` and `checks.only_known_numbers`, with a code-built fallback.
- Don't commit `.env`, `school.db`, `db/` or model files.
- Run tests only when Hassan asks. Don't run the full suite (`pytest` plus `pnpm test:e2e`) on every change or before merging: it takes his time. When a change needs a check, run only the tests for that part (e.g. `pytest -k manager`).
